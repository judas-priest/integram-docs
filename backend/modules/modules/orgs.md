# Module: orgs

**Path:** `src/api/v2/modules/orgs/`
**Files:** `router.js`, `service.js`, `org-invitations.js` (приглашения по почте), `pm-aggregation.js` (кросс-проектные сводки PM), `pm-listeners.js` (инвалидация их кэша). Уровень роли в SQL и обратно — общий `registry/role-utils.js`
**Base URL:** `/api/v2/orgs/...`  (no `:db` — global)
**Auth:** JWT required for all endpoints.

## Purpose

Organizations group workspaces under a shared identity (company or team). An org has a unique slug and a member list with roles. Workspace creation can reference an `org_id`.

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| GET | `/orgs` | List orgs current user belongs to |
| POST | `/orgs` | Create org (`name`, `slug`) |
| GET | `/orgs/:slug` | Get org details |
| PUT | `/orgs/:slug` | Update org name |
| DELETE | `/orgs/:slug` | Delete org (owner only) |
| GET | `/orgs/:slug/members` | List org members (`?page=&pageSize=`); ответ несёт `myRole` — роль вызывающего |
| POST | `/orgs/:slug/members` | Add member by email (`role`: owner/admin/editor/viewer) |
| PUT | `/orgs/:slug/members/:id` | Update member role |
| DELETE | `/orgs/:slug/members/:id` | Remove member |
| POST | `/orgs/:slug/leave` | Выйти из организации самому |
| POST | `/orgs/:slug/transfer` | Передать владение (`{ userId }`) |
| POST | `/orgs/:slug/invite` | Пригласить по почте (`email`, `role`: admin/editor/viewer) |
| GET | `/orgs/:slug/invitations` | Приглашения организации |
| DELETE | `/orgs/:slug/invitations/:id` | Отозвать приглашение |
| GET | `/orgs/:slug/workspaces` | Рабочие области организации (`?page=&pageSize=`) |
| POST | `/orgs/:slug/workspaces` | Привязать область (`{ workspace: 'slug' }`) |
| DELETE | `/orgs/:slug/workspaces/:ws` | Отвязать область |
| GET | `/orgs/:slug/pm/my-issues` | Задачи из всех областей организации |
| GET | `/orgs/:slug/pm/people` | Команда + PM-статистика |
| GET | `/orgs/:slug/pm/portfolio` | Портфель проектов |

Сводки PM описаны в `pm.md` — здесь только перечень путей.

## Slug Rules

- 3–64 characters
- Lowercase alphanumeric, `-`, `_`
- Must start with a letter
- Regex: `/^[a-z][a-z0-9_-]{1,62}[a-z0-9]$/`

## Roles

`owner` | `admin` | `editor` | `viewer` — same role hierarchy as workspaces.

Only the org owner can delete the org. Members can only be managed by org owner/admin.

## AI-инструменты

Группа `orgs` — 13 инструментов. Активируется запросом `search_tools("организации")`
(синонимы того же псевдонима — `orgs`, `org`). Своих синонимов у группы долго не
было вовсе, и открывалась она только текстовым совпадением слова запроса с именем
и описанием — то есть по одному инструменту и не вся.

Уровень риска — `ai/agent/risk-tiers.js`, он же единственный источник правила
подтверждения: `HITL_TOOL_SET` (`ai/agent/middleware.js`) собирается фильтром
`tier === TIER_HIGH`, а `HITL_TOOLS` (`ai/agent/llm.js`) — тем же фильтром. Значит
подтверждение спрашивается ровно у инструментов уровня HIGH; у всех семи в
`tool-executor.js` есть `savePendingHitl` и ветка исполнения после подтверждения в
`ai/agent/index.js`.

| Инструмент | Риск | Подтверждение | Что делает |
|---|---|---|---|
| `list_orgs` | LOW | нет | Организации текущего пользователя |
| `get_org` | LOW | нет | Организация по slug |
| `create_org` | HIGH | да | Создать организацию |
| `update_org` | MEDIUM | нет | Переименовать организацию |
| `delete_org` | HIGH | да | Удалить организацию (только владелец) |
| `list_org_members` | LOW | нет | Участники страницей: `items` + `total`, `page`, `pageSize` |
| `add_org_member` | HIGH | да | Добавить участника по почте; роль — `admin`/`editor`/`viewer`, по умолчанию `viewer` |
| `remove_org_member` | HIGH | да | Удалить участника |
| `transfer_org_ownership` | HIGH | да | Передать владение участнику; прежний владелец остаётся администратором |
| `leave_org` | HIGH | да | Выйти из организации самому |
| `invite_to_org` | HIGH | да | Пригласить по почте; роль — `admin`/`editor`/`viewer` |
| `revoke_org_invitation` | MEDIUM | нет | Отозвать неиспользованное приглашение |
| `list_org_invitations` | LOW | нет | Приглашения организации |

Роли в `add_org_member` и `invite_to_org` перечисляются по CHECK'ам таблиц, а не
по памяти: `_v2_memberships.role` знает `owner`/`admin`/`editor`/`viewer`,
`_v2_invitations.role` — три без `owner`. Роли `member` в платформе нет; будучи
объявленной в перечне инструмента, она доходила до INSERT и роняла добавление
участника пятисотым на нарушении CHECK. Владение не выдаётся добавлением —
только `transfer_org_ownership`.

Сводки PM организации (`pm_org_my_issues`, `pm_org_workload` — состав команды с
загрузкой, `pm_org_portfolio`, `pm_org_create_issue`) живут в группе `pm`, а не
здесь.

## DB Tables

- `_v2_orgs` (global public schema) — `id`, `name`, `slug`, `owner_id`, `created_at`
- `_v2_memberships` (global public schema) — членство и в областях, и в организациях: строка с заполненным `org_id` — членство в организации, с `workspace_id` — в области. Отдельной таблицы `_v2_org_members` нет
- `_v2_workspaces.org_id` — привязка области к организации. Внешнего ключа на `_v2_orgs` нет

## Поведение, о котором стоит знать

- `DELETE /orgs/:slug` перед удалением записи сбрасывает `org_id` у всех рабочих
  областей организации. Внешнего ключа на `_v2_orgs` нет, и без сброса область
  осталась бы привязанной к удалённой организации навсегда — привязать её к новой
  уже нельзя, `attachWorkspace` отвечает 409 «уже принадлежит другой
  организации».
- `GET /orgs/:slug/members` кладёт в тело ответа `myRole` рядом с `currentUserId`.
  Вывести роль вызывающего из строк страницы нельзя: своей строки на странице
  может не быть, и экран, искавший себя среди загруженных, у администратора за
  50-й строкой получал `null` — то есть молча терял правку роли и удаление.
- Роль пользователя в организации сворачивается по числовому старшинству
  (`registry/role-utils.js`), а не строковым `MAX()`: строк членства на одну пару
  пользователь-организация может быть несколько (UNIQUE считает NULL
  различными), а максимум по алфавиту дал бы `viewer` вместо `owner`. Тем же
  модулем пользуется `pm-aggregation.js`.
- Сводки PM (`/orgs/:slug/pm/*`) видят область, если у пользователя есть любое из
  трёх: прямое членство, членство в организации, владение областью. Владелец
  самой организации видит все её области — фильтр к нему не применяется вовсе,
  поимённой строки членства у него может не быть. Та же модель, что в
  `resolveEffectiveRole`; прежний JOIN требовал только прямого членства, и
  участник, добавленный в организацию, а не в область, видел пустой портфель.
- Привязать область к организации может только тот, кто в самой области владелец
  или администратор. Прежде хватало роли администратора В ОРГАНИЗАЦИИ, а так как
  членство в организации даёт роль в её областях, любой вошедший мог завести свою
  организацию, привязать чужую область по slug и получить в ней владение.
- Отвязать может администратор организации ИЛИ администратор области: отвязка
  права сужает, а не расширяет, и владелец области не должен оставаться запертым.
- `POST /orgs/:slug/transfer` передаёт владение участнику организации: прежний
  владелец остаётся администратором, принимающий получает роль owner.
- `POST /orgs/:slug/leave` — выход из организации. Владелец сперва передаёт
  владение, последний администратор назначает преемника.
- `POST /orgs/:slug/invite` заводит приглашение по почте (`_v2_invitations` с
  `org_id`); принимается тем же маршрутом, что и приглашение в область.
  Роль владельца не приглашается — CHECK таблицы знает только admin/editor/viewer.
- Списки участников и областей отдаются страницей: `?page=&pageSize=`, в ответе
  рядом с `data` идут `total`, `page`, `pageSize`.
- Сводка портфеля возвращает `truncated` и `limit`: областей в организации может
  быть больше, чем помещается в выдачу.
- Оба действия доступны и на экранах: выход — на экране участников
  (`OrgMembers.vue`), передача владения — в настройках организации
  (`OrgSettings.vue`); служба фронтенда зовёт их как `orgsService.leave` и
  `orgsService.transferOwnership`.
- Почта в приглашении приводится к нижнему регистру и обрезается по краям.
  Платформа хранит почту в нижнем регистре (`auth/service.js`, `emailLc`), а
  `acceptInvitation` сверяет её точным равенством: приглашение на
  «User@Example.com» без приведения не смог бы принять никто.
- `page` и `pageSize` проверяются зодом ДО службы: негодное значение даёт 400, а
  не 500. `parsePagination` доверяет `page` как есть, и `?page=0` превращался в
  `OFFSET -50` — Postgres на это отвечает ошибкой, а `?page=abc` давал
  `OFFSET null`.
- Признак усечения портфеля считается по числу строк запроса, ДО отсева областей
  с выключенным модулем PM. Счёт по остатку молчал бы там, где из пятидесяти
  отданных строк две отсеяны: сорок восемь меньше предела, хотя выдача усечена.
- Приглашение принимается экраном `/invites/:token/accept`
  (`frontend/src/views/auth/InviteAccept.vue`). Экран живёт вне `AppLayout` и
  помечен `requiresGlobalAuth`: неавторизованного получателя сторож
  маршрутизатора уводит на вход с `?redirect=`, а после входа или регистрации
  возвращает обратно. До 15.08.2026 маршрута не было вовсе, и ссылка из письма
  вела в «страница не найдена» — пригласить было можно, войти по приглашению
  нельзя.
- В выбор «привязать область» попадают только области, где приглашающий владелец
  или администратор, и только ещё не привязанные — перечень привязанных берётся
  полным (`pageSize=1000`), а не с видимой страницы.
- Экраны «Задачи» и «Команда» показывают предупреждение об усечении по полям
  `truncated`/`limit`, как и портфель.
- Задачу в области организации можно создать с экрана «Задачи»; в выбор попадают
  области, где у пользователя роль не ниже `editor` — этого же требует служба.
- Тело `POST /orgs/:slug/pm/issues` проверяется зодом: `workspace` и `title`
  обязательны, негодный запрос даёт 400. Прежде тело не проверялось вовсе, а
  колонка `title` объявлена `NOT NULL` — запрос без названия доезжал до вставки и
  возвращался 500 от Postgres. Схема помечена `passthrough`: прочие поля задачи
  (`priority`, `assigneeId`, `dueDate`…) разбирает служба PM, и отрезать их на
  входе нельзя.
- Управляющими считаются и `admin`, и `owner`. Счёт только по `admin` запирал
  прежнего владельца после передачи владения: выйти нельзя (он последний
  `admin`), понизить себя нельзя (самоудаление запрещено), а организация всё это
  время управляема. Правило одно во всех трёх местах — `updateOrgMember`,
  `removeOrgMember`, `leaveOrg`.
- Сводки PM кэшируются на 60 секунд (`pm-aggregation.js`, ключи `pm_org:<slug>:…`).
  Сброс идёт двумя путями: отложенным слушателем событий PM (`pm-listeners.js`,
  окно 200 мс — свёртка каскадных событий) и синхронно в `createIssueInWorkspace`
  сразу после создания задачи. Второй путь появился потому, что экран
  организации перечитывает сводку немедленно после ответа и успевал прочитать
  её из кэша: задача создана, а списка её не видно до перезагрузки.
- Состояния приглашений на экране печатаются по-русски (`ожидает`, `принято`,
  `просрочено`, `отозвано`); просроченность считается по дате, а не по полю
  `status` — оно меняется на `expired` только при попытке приёма.
- Кнопка удаления организации показывается только владельцу: `deleteOrg` сверяет
  `owner_id`, и администратору она отвечала отказом.
