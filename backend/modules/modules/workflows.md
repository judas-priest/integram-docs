# Module: workflows

Событийные процессы (State Transition Operations) — декларативная спека процесса + append-only журнал событий (ADR-036).

**Path:** `src/api/v2/modules/workflows/`
**Files:** `router.js`, `service.js`, `validators.js`
**Base URL:** `/api/v2/:db/workflows/...`
**Auth:** JWT required. Все осмысленные ручки: `editor`. Health — без JWT (мониторинг).

## Назначение

ADR-036: процесс описывается декларативной спекой (события, переходы, ворота, роли), состояние объекта — последняя строка его append-only журнала.

- **Спека + валидация при записи** — любая правка спеки прогоняет валидатор по всему процессу в той же сделке; нарушение откатывает правку (422 SPEC_INVALID). Битую спеку записать нельзя.
- **Append-only журнал** — UPDATE и DELETE по журналу заглушены правилами БД (`DO INSTEAD NOTHING`). Ошибка «поминается, а не стирается»: исправление выражается компенсирующим событием.
- **STO (State Transition Operation)** — запись события проверяет смежность перехода, ворота (gate_requires), роль и терминальность; все проверки внутри сделки, задний заслон гонки — UNIQUE-индекс.

### Портальная поверхность

`POST /api/v2/:db/portal/api/workflows/events` (modules/portal/router.js) — тот же `recordEvent`, актёр — портальная личность. **Только staff** (`requireStaffPortalJwt`, fail-closed — не `portalAuth('*')`): `requireStaffPortalJwt` заодно перепроверяет членство (U33), а пустые `roles` в спеке не разворачивают ручку всем клиентам. Rate limit 60/мин. Клиенты попадают через контур Входящих (PM-154), не напрямую. Схема тела принимает только `process, objectId, key, fields, causeId, expectedSeq` — **`docId` не принимается**, то есть портальные события не несут документного провенанса (portal/router.js, wfEventSchema).

## Валидатор спеки

`validators.js` — чистая функция `validateSpec(rows, conditionsByProcess, stagesByProcess, { lint } = {})`, без доступа к БД. Вход — строки `_v2_workflow_specs`, выход — нарушения `{ code, event, message }` (process-level дефекты — `event: null`); две проверки #253 ставят `severity: 'warn'`. Группировка по процессам; проверяются шесть групп правил R1–R6 (R1 — ключ обязателен, R2 — дубликаты ключей, R3 — неизвестные `next_keys`, R4 — ровно один старт, R5/R6 — достижимость) плюс два warn-правила (issue #253):

| Code | Проверка | severity |
|------|----------|----------|
| `KEY_REQUIRED` | у строки нет непустого (после trim) ключа | блокирует |
| `KEY_DUPLICATE` | ключ встречается в процессе более одного раза | блокирует |
| `NEXT_UNKNOWN` | `next_keys` ссылается на несуществующий ключ | блокирует |
| `START_COUNT` | стартовых событий не ровно одно | блокирует |
| `TERMINAL_UNREACHABLE` | от старта не достижим ни один терминальный узел | блокирует |
| `EVENT_UNREACHABLE` | есть события, недостижимые от старта (BFS по next_keys) | блокирует |
| `GATE_UNKNOWN` | токен `gate_requires` не существует ни в одном процессе воркспейса; только при `lint: true` (вызывающий передал строки ВСЕХ процессов — write-путь видит один процесс, где кросс-процессная ссылка неотличима от опечатки) | warn |
| `NO_TERMINAL_EXIT` | из достижимого от старта не-сигнального состояния не достижим ни один терминал (обратный BFS; включается только при `hasReachableTerminal`, иначе дублирует `TERMINAL_UNREACHABLE`) | warn |

Кросс-процессные гейты легальны: рантайм (`gateOk` в service.js) ищет чужие ключи в глобальном журнале объекта.

Валидация выполняется **при записи**: каждая CRUD-правка спеки — сделка «INSERT/UPDATE/DELETE → перечитать процесс → validateSpec → откат при нарушении» (assertSpecValid, 422 SPEC_INVALID с details); warn-нарушения фильтруются перед бросанием — живые спеки с тупиковыми ветками продолжают сохраняться, их называет только линтер полной спеки (`lint: true`). Отказ уникального индекса по key (23505, включая wrapped `.cause` настоящего execSql) переводится в 422 SPEC_INVALID, а не 500.

**Bulk — единственный способ собрать новый процесс.** `PUT /specs/process/:process` — одна сделка: DELETE всех строк процесса → INSERT присланных → validateSpec; пустой `rows` сносит процесс. Построчная сборка через POST невозможна: промежуточное состояние процесса нарушает R3/R5 (ссылки на ещё не вставленные ключи, недостижимость) и откатывается. `process` в PUT не переносится — строку нельзя увести в другой процесс, оставив тот битым.

## Валидация полей события

`validateFields(submitted, specFields)` (validators.js, чистая функция) — значения payload против описания полей `spec.fields` целевого события. Вызывается в recordEvent после проверки роли, до optimistic-проверки seq; отказ — 422 SPEC_INVALID, `err.details` несёт перечень сообщений по каждому полю. Проверяются три рода:

| Проверка | Условие |
|----------|---------|
| required | `required: true` и значение пустое (`undefined` / `null` / `''`) — отказ; необязательное пустое пропускается молча |
| тип | `type: 'number'` и непустое значение не приводится к числу (`Number.isNaN(Number(val))`) |
| select options | `type: 'select'` без `source`, с непустым массивом `options`, значение не входит в `options` |

**`source` не проверяется.** Select с `source` — динамический список, набираемый в UI на момент показа формы; серверу нечего сверять его с, и подстановка вариантов на бэкенде не делается (ADR-036 «Не делаем»). Пустой `options` тоже не проверяется — список могли не задать. Поля, присланные сверх спеки, не отбрасываются и не отвергаются — в журнал идёт payload как есть.

## Таймеры (отложенные порождения)

Колонка `timer` спеки — «догоняющие» события: когда с последнего события-якоря прошло N дней, а порождение в этом цикле ещё не записано — записать его от имени системы. Формат строки: **`days:N;after:K;spawn:K2`**, по одному таймеру на строку (несколько таймеров — переводом строки `\n`).

- **Чистая логика** — `timers.js`: `parseTimers(raw)` разбирает строку (пара без двоеточия в части или отсутствующий `days/after/spawn` выкидывает таймер целиком), `findDueSpawns(specRows, journal, now)` по журналу ОДНОГО объекта находит последние события по ключу (при равных `occurred_at` берёт позднюю запись) и возвращает порождения, у которых якорь есть, срок вышел (`elapsedDays >= days`), а порождения после якоря не было. Порог строго «прошло N дней и больше» — меньше N дней тик молчит.
- **Идемпотентность** — единственная: spawn записывается, только если последнего `spawn`-события с момента якоря ещё нет (`spawnedAt < anchorTime`). Отдельного реестра «кто уже выполнен» нет — журнал сам себе реестр. Следствие: если таймер сняли со спеки, а потом вернули с тем же `spawn`, повторной записи не будет (порождение в цикле уже есть); новый виток цикла (новый якорь) открывает новый срок.
- **Исполнитель** — `timers-cron.js`: BullMQ repeatable-джоба **`wf-timers`** в очереди `automations`, cron `0 * * * *` (ежечасно; точность таймера — дни, час погрешности). Регистрация — `registerTimersCron` при старте v2 (v2/index.js, только когда BullMQ активен; прежние repeatable с тем же именем снимаются — смена cron не оставляет второе расписание, приём upsertCronJob). Маршрут джобы — ветка в `processAutomationJob` (automations/worker.js) → `runTimersTickAll`: тик по каждой области из `_v2_workspaces`, внутри — процессы с непустым `timer` → объекты с журналом процесса → `findDueSpawns` → каждая порождение через `recordEvent` актёром **`система`** с `cause_id` = событие-якорь (происхождение видно в биографии). Отказ любого шага — `logger.warn`, тик никогда не бросает; отказ recordEvent не глушит остальные порождения.
- **Ограничение**: актёр `система` должен проходить проверку ролей — событие-порождение с непустым `roles` без этого токена будет отвергнуто (non-fatal warn каждый тик).

## Cross-process gate

`gate_requires` сверяется с **глобальными** pastKeys объекта, а не только с потоком процесса. Перед проверкой ворот recordEvent снимает `SELECT DISTINCT key FROM <events> WHERE object_id = ?` (без фильтра по `process`) — ключ, записанный другим процессом того же объекта, засчитывается. Сценарий: два процесса на один объект (например, договор и его оплата), ворота одного ссылаются на событие другого — per-process stream такого ключа не содержит, и раньше переход был бы заблокирован навсегда.

- **Смежность (`next_keys`) и терминальность остались per-process** — переходы судятся только внутри своего потока; чужой процесс не открывает переходов. Global pastKeys используются ТОЛЬКО в фильтре ворот.
- **Межпроцессные «Следующие» не делаются**: `next_keys` на ключ чужого процесса — ошибка спеки (NEXT_UNKNOWN внутри своего процесса), а автопорождающей связности между процессами нет; каждая связь процессов выражается воротами и/или таймером.

## Роль-токены по поверхностям

`spec.roles` сверяется **точным совпадением** с токеном актёра (`csvList(roles).includes(actor)`), без масок и префиксов. Токен одной поверхности не матчит другую — fail-closed:

| Поверхность | Актёр |
|-------------|-------|
| REST workspace / MCP (agent-путь) | `username` из JWT (`req.v2user.username`); при отсутствии username — числовой `req.v2user.id` (фолбэк router.js, `String(req.v2user?.username ?? req.v2user?.id ?? '')`) |
| Портал, staff | `username` из `_v2_users` (`resolvePortalUsername`) |
| Портал, клиент | `portal:<clientObjectId>` |

Пустой `roles` = событие разрешено любому актёру, прошедшему ручку (на портале ручку гасит staff-only JWT). Для автоматизаций/агента актёр приходит отдельным путём (T4b/`ctx.userName` в resumeAfterHitl).

## EAV-привязка событий

Событие знает, чей это объект. На строке спеки — `object_table_id` (id EAV-таблицы области); при записи STO он переписывается на строку журнала вместе с `subject_kind = 'eav'` (DEFAULT; колонка готова для не-eav субъектов — этап 3, сейчас любой субъект eav).

Проверка существования объекта при записи (recordEvent, шаг 1a): `SELECT id FROM <главная EAV-таблица> WHERE id = ? AND up = 1 AND t = object_table_id` — корневой объект (`up = 1`) именно таблицы процесса. Два заслона в одном условии: без `up = 1` событие сослалось бы на строку дочерней таблицы, без `t = ?` — на чужой объект другой таблицы (id сталкиваются между таблицами: один id живёт и в 308, и в 310). Когда `object_table_id` в спеке не указан — проверяется только существование корня (`id + up = 1`), без принадлежности таблице.

## Атрибутный журнал (подход Балдачева, PM-242)

Изменения реквизитов привязанной таблицы дописываются в тот же журнал отдельным процессом `'@attr'` (ключ события `attr.changed`, `fields = { reqId, old, new }`) — параллельный поток, БЕЗ спеки и смежности: атрибутный поток не участвует в состоянии процессного и не мешает его переходам.

- **Привязка**: `_v2_workflow_bindings (table_id, attr_journal)`; управление — `GET /bindings`, `PUT /bindings/:tableId` (UPSERT одним запросом). Привязки ставятся только через API, кэша нет: слушатель делает 2 point-SELECT на изменение (тип объекта из главной EAV-таблицы — payload `requisite.changed` не несёт typeId, затем привязка). Кэш — при появлении CRUD-нагрузки, не раньше.
- **Слушатель**: `listeners.js` подписан на `object.requisite.changed` (8 эмиссий в objects/service.js) через `sideEffect('workflows:attr-journal', …)`; регистрация — в v2/index.js рядом с маунтом роутера. Цикла нет: автоматизации переэмитят `object.updated` с `_chainDepth`, но `requisite.changed` никогда не переэмитится, а `@attr`-поток реквизиты не пишет.
- **seq** одного INSERT'ом через подзапрос `MAX(seq)+1` по потоку `'@attr'` объекта; задний заслон — тот же UNIQUE `(process, object_id, seq)`, проигравший гонку молча выходит (23505 → warn, сосед уже дописал).
- **Зафиксированное упрощение**: emit `requisite.changed` происходит ВНУТРИ сделки `updateObject`, поэтому sideEffect может стартовать до COMMIT бизнес-операции — откатённая бизнес-правка способна оставить атрибутное событие в журнале. Журнал append-only, править событие нельзя: исправление — компенсирующая запись, не правка. Non-fatal по построению: любая ошибка журнала не ломает бизнес-запись (try/catch целиком).

## Хэш-цепочка журнала (02.10.2026)

Каждое событие при вставке несёт `prev_hash` и `hash = sha256(prev_hash + '|' + canon)`, где канон — стабильная JSON-строка содержимого (process, objectId, key, actor, seq, fields, causeId, objectTableId, subjectKind, docId; ключи отсортированы рекурсивно — `workflows/chain.js`). Хэш попадает в строку ТОЛЬКО при INSERT: UPDATE/DELETE глушатся RULE'ами, задняя правка невозможна технически — правка выразилась бы в изменённом hash при неизменном prev, что и ловит верификатор.

- **Сериализация**: `pg_advisory_xact_lock(hashtext(db))` внутри транзакции записи — параллельные вставки строят цепочку, а не вилку. Закрыты оба писателя: `recordEvent` (STO) и `recordAttrEvent` (@attr-поток, переведён в транзакцию; прежний одиночный INSERT..SELECT не позволял считать хэш).
- **Цепочка начинается с момента включения**: события до выкладки остаются с `hash IS NULL` («preChain») — задним числом дописать их нельзя (UPDATE глушится).
- **Верификация**: `GET /workflows/chain/verify` перечитывает журнал (ORDER BY id) и пересчитывает; `{ok:false, firstBreak:{id, reason}}` = задняя правка или вилка. Чистые функции канона/хэша/верификации — `chain.js`, тесты `__tests__/chain.test.js` (9) + `chain-write.test.js` (контракт INSERT).
- Строка `fields` (JSONB) канонизируется рекурсивно: порядок ключей в записи не влияет на хэш.

## Провенанс документов

Событие может нести `docId` — ссылку на документ области как на артефакт-основание (например, «Подписано» со ссылкой на скан договора).

- **Проверка при записи** (recordEvent, шаг 1b): прямой SELECT `id + deleted_at IS NULL` по `_v2_documents` — документ обязан существовать и быть неудалённым. Доступ НЕ проверяется намеренно: это провенанс (фиксация основания), а не разграничение.
- **Обратный список**: `GET /docs/:docId/events` — все события журнала, сославшиеся на документ (`WHERE doc_id = ? ORDER BY seq`). Журнал append-only, поэтому список переживает удаление документа: документ уходит в soft-delete, ссылки на него остаются и читаются.
- **Портальная поверхность без docId**: `POST /:db/portal/api/workflows/events` принимает только `process, objectId, key, fields, causeId, expectedSeq` — `docId` в схеме нет, и портальные события документного провенанса не несут (см. «Портальная поверхность»).

## KAG-проекция

После COMMIT каждого процессного события (только при известном `object_table_id`) в граф знаний пишется проекция — non-fatal sideEffect `workflows:kag-projection`, отказ логируется и на событие не влияет:

- сущность `wf_event_<id>` (entityType `wf_event`, свойства: process, objectId, key, docId);
- связь ABOUT → `eav_<table>_<obj>` (ЗАРЕЗЕРВИРОВАННЫЙ id: проекция объектов EAV в KAG — этап 3, пока связь «висячая», traversal её не отдаёт);
- при `causeId` — связь CAUSED_BY → `wf_event_<causeId>` (причинная цепочка журнала, ≡ `bas:CausalLink` онто-моста onto-словаря).

Импорт ленивый (`await import('../swarm-memory/kag.js')`): kag.js тянет llm-router и тяжёлые зависимости, не нужные большинству вызовов recordEvent и тестам. Без `object_table_id` проекция не выполняется — ABOUT-цель была бы синтетической. Стоимость: один embedText на событие внутри kag-импорта — помнить при масштабе (поток `@attr` не проецируется, только процессные события).

## Темпоральная роль

Онтология платформы — три слоя (onto #1: табличный, графовый, OWL). Workflows даёт **темпоральный слой**: append-only журнал с `seq` и `occurred_at` — «как жизнь течёт», а не «как сейчас». В onto-словаре этот слой честно назван дырой; модуль — его платформенный носитель.

## Ловушки

- **cause_id — provenance проверяется**: ссылка обязана вести в журнал ЭТОГО же объекта того же процесса (`recordEvent` проверка 2); иначе 422 SPEC_INVALID «Причина не из истории этого объекта».
- **Компенсирующие записи вместо правки** — журнал append-only на уровне БД; UPDATE/DELETE молча глушатся правилами, исправление — новое событие.
- **history без лимита** — `getState` отдаёт всю биографию объекта; при длинных процессах (тысячи событий) это унесёт payload. Backlog: cap + total при длинных процессах. `@attr`-поток усугубляет: частые правки реквизитов раздувают историю объекта быстрее процессных событий.
- **Чтение ничего не судит** — `state.available` ставит `blocked` только по воротам; роль на чтении не применяется (актёр в момент чтения неизвестен, проявится при попытке записи).
- **`actor`/`prompt` спеки** — справочные, сервером не исполняются (исполняются gate_requires, roles, next_keys, is_start, fields — «Валидация полей», timer — «Таймеры»).
- **Ключ спеки переименовали после записи** — журнал ссылается на события по `(process, key)`, не по id спеки; старые записи журнала перестают находить свою строку спеки (кандидаты молча не дают переходов).
- **up = 1 only** — проверка существования допускает только корневые объекты; объекты дочерних таблиц процессов быть не могут (child-table записи живут под родителем и процессом не считаются).
- **Атрибутные события до COMMIT** — см. «Атрибутный журнал»: откатённая бизнес-правка может оставить `attr.changed` в журнале; исправление — компенсирующая запись.
- **KAG растёт без TTL** — проекции `wf_event_*` и их связи не удаляются никогда; граф растёт монотонно вместе с журналом.

## Связь с ADR-036

Полная спека решения — `docs/adr/036-process-spec-module.md`. «Не делаем»: слои 2062/2063 и ИСТОК не трогаются — модуль живёт своими сателлитными таблицами рядом с EAV. Плюс решения этапа 3:

- **select с `source`** — динамические варианты не сверяются на сервере (см. «Валидация полей»): список набирается в UI, подменять его бэкендом не берёмся.
- **Межпроцессные «Следующие»** — `next_keys` не ссылается на чужой процесс; связность процессов — только ворота (`gate_requires` по глобальным pastKeys) и таймеры.
- **history pagination** — `getState` отдаёт биографию целиком (см. «Ловушки»); cap + total отложены до реальных длинных процессов.
