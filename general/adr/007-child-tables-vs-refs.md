# ADR-007: Child tables (up=parentId) vs ref-колонки

**Статус:** accepted

## Контекст

В EAV-схеме есть два способа связать записи: child table (объекты с `up=parentObjectId`) и ref-колонка (колонка с ссылкой на другой объект). Они решают разные задачи, и путаница между ними ломает UI и бизнес-логику.

## Решение

**Child table** (`up = parentObjectId`) — для **подчинённых** сущностей:
- Записи не существуют без родителя
- Создаются с `parentId` в теле запроса
- Отображаются как вложенные вкладки внутри родительской записи
- Не видны в сайдбаре как самостоятельные таблицы
- В схеме: `baseType = parentTypeId` (child type's `t` указывает на parent type id)
- Примеры: позиции заказа, адреса клиента, этапы задачи, комментарии

**Ref-колонка** (ссылка через EAV) — для **независимых** сущностей:
- Обе стороны существуют независимо
- Удаление ref не удаляет referenced объект
- Хранение: `t=refObjId, val=String(colDefId)` (inverted pattern)
- При каждом создании/удалении ref — `bus.emit('object.edge.created/deleted')` для графа
- Примеры: клиент на заказе, исполнитель задачи, категория товара

## Последствия

- Child records создаются только с `parentId` — без него это корневой объект другого типа
- Child tables в `plan_schema`: поле `parentTableName`; в `create_table`: `parentTypeId`
- Нельзя сделать self-referencing через child table (бесконечная вложенность)
- Ref на удалённый объект создаёт «битую» ссылку — каскадного удаления нет
- При выборе: если запись имеет смысл только в контексте родителя → child table; если живёт самостоятельно → ref
