# ADR-008: Паттерн мультиагентной оркестрации

**Статус:** accepted

## Контекст

Integram поддерживает AI-агентов: оркестратор, agent registry, A2A-протокол, делегирование через `delegate_to_agent`. При разработке фич с несколькими специализированными агентами возникает вопрос: как правильно их координировать?

В индустрии (Anthropic, OpenAI, Google, 2024–2025) сложилось несколько паттернов с принципиально разными трейдоффами.

## Рассмотренные альтернативы

### A. Supervisor — LLM как оркестратор

LLM сам решает, каких агентов вызвать, в каком порядке, с каким контекстом (AutoGen, LangGraph supervisor).

**Проблемы:**
- Нестабильно — LLM может выбрать неверный маршрут
- Дорого — каждый routing-шаг = дополнительный LLM-вызов
- Недетерминировано — одинаковый вход → разный путь выполнения

### B. Handoff — передача управления между агентами

Агент A решает передать управление агенту B, тот — агенту C (OpenAI Swarm, Agents SDK handoffs).

**Проблемы:**
- Непредсказуемый граф выполнения, сложно отлаживать
- Задержка накапливается по цепочке (каждый хоп — +latency, +cost)
- Трудно тестировать: поведение зависит от LLM-решений внутри агентов

### C. Parallelization — код как оркестратор ✓ выбрано

Детерминированный код (не LLM) запускает независимых агентов параллельно и агрегирует результаты. Рекомендован Anthropic в "Building Effective Agents" (декабрь 2024) для задач с независимыми подзадачами.

## Решение

### 1. Оркестратор — всегда код, не LLM

Если маршрут определяем заранее — `Promise.all` в коде:

```js
const [design, quality, knowledge] = await Promise.all([
  callAgent('design-agent', { eco, bom }).catch(e => ({ error: e.message })),
  callAgent('quality-agent', { eco }).catch(e => ({ error: e.message })),
  callAgent('knowledge-agent', { partId }).catch(e => ({ error: e.message })),
])
const risk = worstOf([design.risk, quality.riskLevel])
```

LLM как оркестратор — только когда маршрут нельзя определить без семантического понимания запроса.

### 2. Агент — узкий и stateless

Каждый агент:
- Один узкий системный промпт (конкретная роль, не «всё умею»)
- Минимальный контекст (только то, что нужно для этой задачи)
- Структурированный JSON на выходе, не свободный текст
- Не хранит состояние — контекст передаётся явно при каждом вызове

Широкий промпт деградирует качество. Лучше пять узких агентов, чем один «умный».

### 3. Контекст передаётся явно, не через shared state

Агенты не читают общую память друг друга. Оркестратор собирает нужный контекст и передаёт каждому агенту явно в запросе. Shared mutable state между агентами — источник гонок и непредсказуемости.

### 4. Graceful degradation обязательна

Один упавший агент не блокирует остальных. `.catch` на каждом вызове, агрегация по доступным результатам.

### 5. Human-in-the-loop на высоком риске

Агенты рекомендуют — человек решает. Финальное действие (approve, deploy, delete) требует явного подтверждения. Автоматическое выполнение — только для low-risk операций (read-only, уведомления).

### 6. Реализация в Integram

| Потребность | Механизм |
|---|---|
| Специализированный агент без отдельного сервиса | Connector к LLM API с индивидуальным системным промптом |
| Внешний агент (отдельный сервис) | Agent Registry + A2A JSON-RPC (`tasks/send`) |
| Оркестрация из portal custom_code | `api.runConnector()` / `api.runAgent()` в `Promise.all` |
| Делегирование из основного агента | Инструмент `delegate_to_agent` (для семантической маршрутизации) |

### 7. Observability — не опциональна

Каждый агент-вызов логирует: входной контекст, выходной результат, latency, token count, trace ID (чтобы связать все вызовы одного запроса). Без этого мультиагентная система необъяснима при сбоях.

## Последствия

**Запрещено:**
- LLM как маршрутизатор, если маршрут определяем детерминированно
- Shared mutable state между агентами
- Длинные последовательные цепочки без необходимости — каждый хоп увеличивает latency и стоимость
- Высокорисковые действия без HITL-подтверждения

**Упрощается:**
- Тестирование: каждый агент тестируется изолированно (фиксированный вход → ожидаемый JSON)
- Отладка: маршрут явный, читается в коде
- Замена агента: один промпт или один коннектор, остальное не трогаем

**Усложняется:**
- Агрегация частичных результатов при сбое части агентов
- Проектирование контекста: нужно думать, что именно передать каждому агенту

## Антипаттерны — явные нарушения этого ADR

Если в коде или в предложении по архитектуре встречается что-то из списка ниже — это противоречит данному решению. Нужно исправить, а не адаптировать ADR под новый код.

| Антипаттерн | Почему неправильно |
|---|---|
| «Давай сделаем LLM-агент, который сам решает, кого вызвать» | Supervisor-паттерн. Нестабилен, дорог, недетерминирован. Оркестратор — код. |
| «Агенты будут читать общий shared state» | Гонки, непредсказуемость. Контекст передаётся явно через параметры. |
| «Сделаем одного большого агента, который всё умеет» | Широкий промпт деградирует качество. Узкая специализация — обязательна. |
| «Агент сам выполнит действие, потом сообщит пользователю» | HITL обязателен для высокорисковых действий. Агент рекомендует, человек подтверждает. |
| «Запустим агентов последовательно — сначала design, потом quality» | Без необходимости — накапливает latency. Независимые агенты — всегда параллельно. |
| «Если один агент упал — выбрасываем ошибку на весь запрос» | Graceful degradation обязательна. Частичный результат лучше полного отказа. |
| «Не будем логировать вызовы агентов — и так понятно» | Без trace ID и latency/token метрик сбои необъяснимы. Observability — не опция. |
