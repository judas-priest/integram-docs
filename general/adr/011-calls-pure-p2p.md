# ADR-011: Calls module — pure P2P, no SFU/media-server

**Дата:** 2026-05-16
**Статус:** accepted

## Контекст

Нужны аудио + видео звонки внутри Integram (1-1 и одна workspace voice room ≤8).
Альтернативы:

- **Pure P2P mesh** — браузеры соединяются напрямую, сервер только сигналит
- **SFU** (mediasoup, LiveKit) — сервер пересылает медиа
- **MCU** — сервер микширует

Различия по idle-стоимости, потолку участников, операционной сложности и латентности.

## Решение

Чистый P2P mesh: сигналлинг через существующий WS-хаб (`backend/src/api/v2/ws.js`,
канал `calls`), coturn для NAT-обхода, жёсткий лимит 8 участников на комнату.
Никакого медиа-сервера, никаких новых процессов в `dev-start.sh`.

## Последствия

**Положительные:**
- Idle cost = 0: пока никто не звонит — нет медиа-процессов
- Не добавляется демон в `dev-start.sh`, нет нативных зависимостей
- Backend остаётся stateless (состояние только в Postgres + per-process room presence)
- E2E шифрование (DTLS-SRTP между браузерами) не теряется

**Отрицательные:**
- Потолок ~8 участников — mesh масштабируется O(N²) от каждого браузера.
  Митигация: целевая аудитория — SMB команды 3-12 человек; крупные all-hands → внешние сервисы (Zoom).
- Нет записи звонков (требовала бы SFU или recording-бот)
- Один peer = один видео-сендер (нельзя одновременно камера + screen-share для одного PC)

## Альтернативы рассмотренные

- **mediasoup внутри backend-процесса:** отвергнуто. +200MB RAM idle, +1-2с dev reload,
  все звонки рвутся при рестарте бэкенда, нативные deps требуют пересборку при апгрейде Node.
- **mediasoup как отдельный процесс:** отвергнуто. Добавляет процесс в `dev-start.sh`
  и площадь поверхности для ops при неясной выгоде на нашем масштабе.
- **LiveKit (managed или self-hosted):** отвергнуто. Внешняя зависимость, ломает принцип
  "всё на Node, полный контроль".
- **Rust SFU (str0m/medea):** отвергнуто. Не решает проблему +1 процесса, добавляет язык в стек.
