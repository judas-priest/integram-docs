# ADR-016: Объектный слой — канонические объекты поверх разнородных источников

**Статус:** proposed

## Контекст

Нужен коннектор разнородных источников (1С, Bitrix24, системы учёта) в единую модель
данных так, чтобы агент работал с **бизнес-объектами и их связями**, а не со строками
семи систем (эффект Palantir Foundry Ontology).

Главная трудность — один и тот же товар называется и кодируется по-разному:
- в бухгалтерии 1С — «банк к»,
- в цехе — «банк основная»,
- в продажах Bitrix — «банка сгущёнки 380г».

Это **три разные задачи**, которые путают:
1. **Маппинг схем** (поле↔поле) — структурный.
2. **Разрешение тождества** (запись↔запись) — «это один и тот же физический товар».
3. **Ролевое именование** (одна вещь — много имён по роли/контексту) — это не грязь
   данных, а перспектива: имя принадлежит отношению «роль↔вещь», а не самой вещи.

## Что в integram УЖЕ есть (строим на этом)

| Нужно | Уже есть | Путь |
|---|---|---|
| Приём из внешних API + маппинг полей + upsert | модуль `connectors` (JSONB config: `mapping`, `auth`, `pagination`, `incremental`, `writeMode: upsert`, presets, CDEK/Pochta) | `modules/connectors/` |
| Извлечение/нормализация в EAV | `normalizer` (classifier→extractor→**resolver**→populator) | `modules/normalizer/` |
| **Разрешение тождества + подтверждение человеком** | агент `resolver` + HITL `POST /normalize/:jobId/confirm-resolution` (кластеры с overrides) | `modules/normalizer/agents/resolver.js` |
| Объекты и связи | EAV (`objects`), граф (`graph_objects`/`graph_edges`), KAG | `modules/objects`, граф |
| Семантическая близость | pgvector (hybrid search) | swarm-memory |

Вывод: слой 1 (приём+маппинг) и слой 3-часть (резолюция+HITL) — построены. Не хватает
**канонического тождества сквозь источники, ролевых алиасов и провенанса**.

## Решение

### 1. Канонический объект + ролевые алиасы (НЕ схлопывать имена)

Тип `Product` (канонический объект, стабильный внутренний id) и отдельный тип
`ProductAlias` (child table к Product):
```
ProductAlias { product_id, name, role, source_system, source_pk, source_code }
```
- «банк к» / role=bookkeeping / source=1С
- «банк основная» / role=shop / source=1С-производство
- «банка сгущёнки 380г» / role=sales / source=Bitrix

Имя — ролевой вид над одним тождеством. Агент отдаёт роль-уместное имя; объект один.

### 2. Тождество сквозь источники — двухслойно

1. **Детерминированно** по сильным ключам: GTIN/штрихкод, GUID-ссылка номенклатуры 1С,
   артикул. Реализуется существующим `writeMode: upsert` коннектора по ключу-свойству
   (закрывает 70–90%).
2. **Вероятностно** для остатка без ключей: pgvector-эмбеддинг {имя+атрибуты} →
   кандидаты-кластеры → существующий **HITL `confirm-resolution`** (человек подтверждает).
   Переиспользуем `normalizer/agents/resolver.js`, расширив на кросс-источниковые записи.

### 3. Провенанс на каждом значении

Свойство канонического объекта несёт источник: `{ value, source_system, source_pk,
fetched_at }`. Конфликт источников (1С цена X, Bitrix цена Y) **держим оба**, не
усредняем; разрешение — правило приоритета источника или человек.

### 4. Сопоставление как акт (подотчётность)

Каждое принятое сопоставление (схема-маппинг, слияние записей) — не строка конфига, а
запись в логе с автором и временем (кто принял). Ошибочное слияние прослеживается до
принявшего. (Связано с моделью ревью-ворот, ADR-015.)

### 5. Кто строит онтологию — петля агентов под надзором

Агенты предлагают, человек принимает (как в sandbox-цикле):
- **researcher** читает схему источника и сэмплы;
- **engineer/extractor** предлагает маппинг полей и кандидатов слияния;
- **opponent** атакует ложные совпадения (два разных товара с похожим именем);
- **controller** сверяет с принятыми решениями (`search_similar_decisions`) и
  регламентом (`kag_search`);
- человек подтверждает через `confirm-resolution` → сопоставление становится актом.

## Границы (КРИТИЧНО — не boil-the-ocean)

- **НЕ строить «онтологию предприятия» сверху.** Старт — **один тип `Product`,
  два источника (1С + Bitrix), под один реальный вопрос** («движение банки от прихода
  1С до продажи Bitrix»). Рост по сценариям.
- Только существующий стек: connectors, normalizer/resolver, EAV, graph, pgvector,
  агенты, BullMQ. **Без** нового движка MDM, без Java/Spark, без внешнего графа.
- Готовые стандарты — только как **скелет**: GTIN/штрихкод как ключ, классификаторы
  (UNSPSC/ОКПД2) как справочник категорий. Инстансный маппинг всегда bespoke.

## Готовое — что переиспользуем (по итогам поиска)

Готового лёгкого open-source аналога Foundry Ontology под Node+PG нет (OpenFoundry —
42 Go-сервиса на K8s, AGPL; каталоги Atlas/DataHub — про метаданные, не объекты).
**Объектный слой строим сами — это ~3–4 таблицы в PostgreSQL.** Берём готовым:

| Компонент | Решение | Лицензия |
|---|---|---|
| Скелет полей Product/Offer/Org | **GoodRelations** / schema.org (+ Gist как верх) | CC BY / CC BY-SA |
| Классификатор категорий | **GS1 GPC** (бесплатно, JSON/XML, **русский**, атрибуты) + мапинг на ОКПД2/ТН ВЭД | бесплатно |
| Ключ экземпляра | **GTIN/штрихкод**; Wikidata `P3962` для обогащения | открыто / CC0 |
| Коннектор 1С | **OData v3** (НЕ v4!) через `axios`/`got` + Basic Auth | — |
| Коннектор Bitrix24 | **`@bitrix24/b24jssdk`** (офиц., Node) + вебхук | MIT |
| Разрешение тождества | **на самом PG**: `pg_trgm` (блокинг) → `fuzzystrmatch` (rescore) → `pgvector` (семантика) | PostgreSQL License |

**НЕ брать:** Zingg (Spark/AGPL), Splink-PG (сырой бэкенд), eCl@ss (платно), Atlas/DataHub
(Hadoop/Kafka), OpenFoundry (K8s/AGPL). Никакого Java/Spark — одна БД держит канон,
алиасы, эмбеддинги и ER-функции.

### Критичные факты интеграции (выверено)
- **1С OData = v3**, не v4 (популярные npm-клиенты целятся в v2/v4 → ручной HTTP надёжнее).
  Номенклатура = `Catalog_Номенклатура`. **Штрихкоды — НЕ реквизит товара**, а отдельный
  регистр `InformationRegister_Штрихкоды`, связь через измерение «Владелец» с приведением
  типа: `$filter=Владелец eq cast(guid'<GUID>','Catalog_Номенклатура')`. Цены — тоже
  отдельные регистры (имена зависят от конфигурации УТ/Розница/УНФ/ERP). Объект надо явно
  открыть в составе OData (`УстановитьСоставСтандартногоИнтерфейсаOData`).
- **Bitrix24**: товары `catalog.product.*` + предложения `catalog.product.sku.*`; товары
  в сделках — `crm.item.productrow.*` (новый). Auth — входящий вебхук.
- **ER**: ~70% дублей закрывает `pg_trgm`; эмбеддинги переоценивают сходство коротких
  SKU (риск over-match) — пороги калибровать на своих данных.

## Последствия

**Плюсы:** агент действует над объектом, не над строками; одно тождество — много
ролевых имён; конфликты источников видимы; построение коннекторов — поднадзорная
петля агентов (дёшево против армии интеграторов).

**Риски:** ложные слияния (митигируется opponent + HITL); качество ключей в 1С/Bitrix
(сначала детерминированный слой, замер покрытия); рост числа алиасов (нормально —
это и есть модель).

## План (пилот)

1. Коннектор-конфиги: 1С (OData) и Bitrix (REST catalog) на существующем `connectors`.
2. Типы `Product` + `ProductAlias` + поле провенанса; ключ-свойство (GTIN/артикул).
3. Кросс-источниковый upsert по ключу (детерминированный слой).
4. pgvector-резолюция остатка → `confirm-resolution` (расширить resolver на коннекторы).
5. Объектно-агентный ответ на пилотный вопрос (движение банки 1С→Bitrix, ролевое имя).

Связано: ADR-015 (ревью/акты), модули `connectors`, `normalizer`.
