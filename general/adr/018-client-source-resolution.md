# ADR-018: Резолюция клиентских данных из источников — golden record + governed writeback

**Статус:** proposed

**Инстанциация [ADR-016](016-object-layer.md)** (объектный слой / эффект Palantir Foundry
Ontology) для типа `Клиенты`. ADR-016 покрыл товары (1С + Bitrix); здесь — клиенты
(UDS + Telegram + портал + xlsx) с добавлением настраиваемого survivorship-движка и
верификации готовности к отгрузке.

## Контекст

Один клиент приходит из нескольких систем с расходящимися данными (имя, телефон, адрес,
email). Сейчас коннектор пишет прямо в таблицу `Клиенты` (309) и **перетирает** —
результат недетерминирован: на одних и тех же данных «истинное» значение может оказаться
разным, а для отгрузки физического товара (мёд) нужен один надёжный телефон/адрес.

Это та же тройка задач, что в ADR-016: маппинг схем, разрешение тождества, ролевое
именование. Не хватает **детерминированного слияния полей в каноническую запись с
провенансом** и **проверяемой готовности к отгрузке**.

## Решение

### 1. Канонический клиент + дочерняя «Источники» (ADR-016 §1)
`Клиенты` (309) — каноническая (золотая) запись. Новая дочерняя таблица
**«Источники клиента»** (`parentId = clientId`): по строке на источник —
`{ Источник (ref 301), имя, телефон, email, raw, captured_at }`. Источник НЕ пишет в 309
напрямую — пишет свою строку-источник. Никто никого не перетирает.

### 2. Тождество — двухслойно (ADR-016 §2)
1. **Детерминированно** по сильным ключам в порядке надёжности:
   `UDS ID` → `Telegram ID` → телефон (нормализованный E.164) → email.
2. **Fallback** (только когда ключей нет, остаётся похожее имя): pgvector/LLM →
   кандидаты → существующий HITL `confirm-resolution`. LLM-выбор логируется как
   требующий подтверждения.

### 3. Survivorship-движок (НОВОЕ относительно ADR-016)
Для каждого поля золотой записи — ранжированный приоритет источников + валидатор
(телефон → E.164, email → формат, и т.п.). Движок берёт первое валидное значение,
пишет в 309. Конфликт, не разрешённый правилами → флаг на HITL (не усредняем — ADR-016 §3).

### 4. Провенанс на каждом значении (ADR-016 §3)
Каждое золотое поле несёт lineage: `{ value, source, sourceRowId, at }`, append-only.
«Поле телефон взято из UDS» — прослеживаемо.

### 5. Governed writeback — Actions Palantir (НОВОЕ, усиление ADR-016 §4)
Золотые поля **не редактируются свободным `update`**. Их меняют только: (а) пересчёт
survivorship-движком, (б) HITL-подтверждённое слияние. Пересчёт, подтверждение слияния и
verify — типизированные операции с risk-tier и аудитом (MCP + REST, dual path по ADR-002).
Каждое сопоставление — акт с автором и временем.

### 6. Адреса — расширяем существующую 314
В дочернюю «Адреса» (314) добавляются `Источник` (ref 301) + `isGolden` (bool). Источники
кладут свои адреса с тегом источника; движок по приоритету ставит `isGolden=true` ровно
одному. Отгрузка читает golden-адрес. Без второй таблицы адресов.

### 7. Верификация готовности к отгрузке (НОВОЕ)
Детерминированный инструмент читает золотую запись → pass/fail + список проблем:
валидный телефон? есть golden-адрес? нет неразрешённого конфликта? Конфликт → HITL.

### 8. Конфиг — на таблице, в конструкторе
Match-ключи, приоритеты источников по полям, валидаторы, обязательные-для-отгрузки поля —
JSONB-конфиг на `typeId` (сателлитная таблица по образцу `_v2_computed_reqs`), редактируется
в конструкторе таблицы. Без хардкода workspace-данных (правило platform/no-hardcode).

### 9. Триггеры — оба
Авто-пересчёт по bus-событию (`object.created`/`object.updated` на строках-источниках) +
принудительный verify перед отгрузкой.

## Границы (наследуем ADR-016 — НЕ boil-the-ocean)

- **Без** Foundry/Spark, версионирования датасетов, enterprise-wide онтологии. Per-workspace.
- Только существующий стек: connectors, normalizer/resolver, EAV, graph, pgvector, bus, BullMQ.
- LLM — только fallback резолюции тождества, никогда не для выбора золотого значения.
- Старт: `Клиенты` + UDS как первый источник; Telegram/портал/xlsx добавляются по сценарию.

## Последствия

**Плюсы:** детерминированное, проверяемое слияние; конфликты видимы, не усредняются;
провенанс на каждом поле; golden-запись неизменяема в обход движка (governed writeback);
готовность к отгрузке — машинная проверка, не «на глаз».

**Минусы/риски:** ложные слияния (митигируется opponent + HITL, ADR-016); сложность
конфига приоритетов (выносим в UI конструктора); чаще пересчитываем при auto-триггере.

Связано: ADR-016 (объектный слой), ADR-002 (MCP+REST), ADR-005 (event bus),
ADR-007 (child tables), ADR-012 (HITL), ADR-015 (ревью/акты).
