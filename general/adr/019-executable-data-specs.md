# ADR-019: Декларативный слой исполняемых спеков данных

**Статус:** proposed

## Контекст

Агенты работают с текстовыми спеками плохо (интерпретируют прозу, дрейфуют,
непроверяемо), с **исполняемыми** — хорошо: спек даёт детерминированный pass/fail,
замыкая петлю generate→verify (как тесты для кода).

В Интеграм уже есть исполняемые правила, но **разрозненно**: column-validation,
computed-reqs (LOOKUP/ROLLUP/FORMULA), automations (процессы), resolution (golden record,
ADR-018) — у каждого свой формат, UI и исполнитель. Не хватает первоклассного понятия
**инвариант данных над таблицей**: декларативное правило «что должно быть истинно для
записи», которое движок принуждает и сверяет. `verify_client_shipping` (ADR-018) — частный
хардкод этого; обобщаем.

n8n рассмотрен и **отвергнут**: это императивный конструктор воркфлоу (≈ модуль automations),
а не декларативный спек-слой. Дублировал бы automations, не дав проверяемости.

## Решение

Новый модуль `specs`: декларативные инварианты над `typeId`.

### 1. Спек = именованный набор правил (AND) над записью
Правило: `{ field, op, value?, validator? }`. Операторы (детерминированные, чистые):
`required`, `notEmpty`, `equals`, `notEquals`, `in`, `matches` (regex), `min`, `max`,
`valid` (через нормализаторы resolution: phone→E.164, email). Спек проходит, если все
правила истинны.

### 2. Детерминированный evaluator (чистая функция)
`evaluateRules(record, rules) → { pass, violations:[{field, op, problem}] }`. Без БД, без
LLM — тестируется юнитами. Поверх: `runSpec` (скан таблицы → нарушающие строки + счётчики),
`checkRecord` (одна запись).

### 3. Конфиг — на таблице, в конструкторе
Сателлит `_v2_data_specs` (type_id, name, definition JSONB, enabled), по образцу
`_v2_computed_reqs`. Редактор `DataSpecsEditor.vue` рядом с другими панелями типа.

### 4. Dual path (ADR-002)
REST `/:db/specs/...` (CRUD + run + check) и MCP-инструменты `list_specs` /
`check_record` / `run_spec`. Агент авторит спек из прозы намерения, движок принуждает/
проверяет, агент читает структурный результат и итерирует.

### 5. AI-Native harness
Спек — это данные: версионируется, диффается, ревьюится. Агент — первоклассный автор и
оператор спеков через governed-инструменты, не потребитель прозы.

## Границы

- MVP — инварианты/ассерты над одной таблицей (предикаты по полям записи). НЕ кросс-табличные
  джойны, НЕ переписывание computed/automations (их объединение — отдельный шаг).
- Только существующий стек: EAV, сателлитные таблицы, bus, dual-path инструменты.
- Принуждение MVP — по требованию (`run`/`check`) + опциональное событие `spec.violated`
  для automations; авто-блокировки записи в MVP нет.

## Последствия

**Плюсы:** проверяемые правила данных для любой таблицы; единый контракт для агента;
verify из ADR-018 становится частным случаем общего спека.

**Минусы/риски:** ещё один движок правил рядом с computed/validation (осознанно — их слияние
позже); скан больших таблиц в `run_spec` ограничивать лимитом/пагинацией.

Связано: ADR-018 (resolution/verify — первый спек), ADR-002 (MCP+REST),
ADR-005 (bus), переиспользует `resolution/validators.js`.
