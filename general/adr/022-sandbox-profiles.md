# ADR-022: Профили песочницы — одно объявление способностей, пределов и таймаутов

**Статус:** accepted
**Дата:** 2026-08-06

## Контекст

Платформа исполняет пользовательский JavaScript в isolated-vm в трёх местах:

| Среда | Кто пишет код | Точка входа |
|---|---|---|
| `automation` | администратор воркспейса | `automations/isolated-runner.js` → `executeIsolated` |
| `workspaceTool` | администратор воркспейса | `workspace-tools/sandbox.js` → `executeBridged` |
| `serverFunction` | тот, кто коммитит в репозиторий codespace; вызывается из портала | `codespace/server-fn-executor.js` → `executeServerFunction` |

Мост один и тот же — `createBridge()` из `isolated-runner.js`. А вот всё остальное разошлось:

- **Три таблицы пределов.** 60/30/15 секунд таймаута, 128/128/64 МБ памяти, три разных набора счётчиков вызовов.
- **Три способа выбирать мосты.** Автоматизации получали мост целиком; воркспейсные тулы — через `selectBridges` по рукописной карте `BRIDGE_REF_NAMES`; серверные функции — через `selectBridges` плюс собственный слой счётчиков поверх счётчиков моста.
- **Три модели способностей.** Воркспейсные тулы валидировали способности по списку в `service.js`; серверные функции парсили комментарий `// capabilities:` вообще без белого списка; автоматизации способностей не объявляли.

Цена расхождения — не эстетическая. Разработчик, переносящий работающий код из автоматизации в серверную функцию, молча получал другое поведение. Три конкретных дефекта, которые прямо следовали из дублирования (см. «Что это уже сломало»).

Отдельный повод: `CSF_LIMITS.agent = 0` выражал «способность запрещена» через «квота ноль». Это разные утверждения, и вызывающий действует по ним по-разному — на исчерпанную квоту ищут настройку, чтобы её поднять.

## Решение

**Способности, пределы и таймауты объявляются один раз — в `backend/src/utils/sandbox-profiles.js`.** Три среды берут оттуда именованные профили.

Различия между средами остаются и должны оставаться — у фоновой автоматизации и у вызова из портала разная цена ошибки. Но они обязаны быть объявлены в одном месте, одинаково названы и одинаково проверяться.

Файл содержит:

- `COUNTER_KINDS` — канонические счётчики (`query`, `mutation`, `fetch`, `ai`, `agent`, `teamchat`).
- `CAPABILITY_BRIDGES` — способность → функции моста, которые она открывает.
- `BRIDGE_COUNTER` — функция моста → счётчик, который она списывает.
- `SANDBOX_PROFILES` — три профиля с `limits`, `forbidden`, `timeoutMs`, `pureTimeoutMs`, `memoryLimitMb`, `gateByCapabilities`.

`createBridge(pool, db, user, wsSettings, profile)` метрирует себя сам по переданному профилю. Второго слоя счётчиков ни у кого нет.

Правила, закреплённые в модели:

1. **Запрет — это отсутствующая способность, а не нулевая квота.** Профиль перечисляет запрещённые способности в `forbidden`; в `limits` соответствующего счётчика нет вовсе. `createBridge` подменяет такие функции моста заглушкой, которая бросает `Capability "agent" is not available in sandbox profile "serverFunction"`.
2. **Незабюджетированный счётчик — это недоступно, а не безлимитно.** Если у профиля нет записи в `limits` для счётчика, мост отказывается работать. Ровно это защищает от дефекта, при котором счётчик молча не считался.
3. **Заглушка, а не удаление.** Запрещённая функция остаётся в мосте как отказывающая. Удалённая всплыла бы как `Cannot read properties of undefined (reading 'apply')` внутри нашей же прослойки — сообщение про нашу обвязку, а не про код автора.
4. **Тир риска остаётся в модели риска.** `workspace-tools/bridges.js` накладывает тиры на `CAPABILITY_BRIDGES` и по-прежнему экспортирует `CAPABILITY_MAP` и `inferRiskTier` в прежнем виде. `utils/sandbox-profiles.js` про тиры не знает.

### Бюджет чтений

Профиль `serverFunction` читает столько же, сколько остальные два (30), а пишет, ходит наружу и зовёт LLM — существенно меньше (10/5/3).

Обоснование: чтение — самый дешёвый вызов из имеющихся, оно уже ограничено `pageSize` и настенным таймаутом. Нет принципиальной причины, по которой сборка данных по десяти таблицам должна быть по карману автоматизации и не по карману серверной функции. А вот запись, исходящий запрос и обращение к LLM имеют побочные эффекты или стоят денег — там строгость к наименее доверенному коду осмысленна.

### Постраничное чтение не бесплатно

Добавлен мост `queryPage()`, возвращающий `{ rows, total, page, pageSize, hasMore, nextCursor }`.

`query()` возвращает голый массив и выбрасывает `meta`. Скрипт, запросивший таблицу длиннее `pageSize` (50 по умолчанию, 1000 максимум), получал усечённый ответ и **не имел способа это заметить** — при том что молчаливое усечение у нас прямо запрещено. `queryPage()` отдаёт `total` и `hasMore`, чтобы вызывающий либо дочитал, либо честно сказал, что показывает не всё.

Страница по-прежнему списывает счётчик `query`. Страница — это реальный поход в базу; бесплатная страница просто переселила бы разгонный цикл из `query()` в `queryPage()`.

## Последствия

**Упрощается.** Изменение предела или таймаута — одна правка в одном файле. Новая способность добавляется в `CAPABILITY_BRIDGES` и автоматически становится видна валидации воркспейсных тулов, парсеру заголовка серверных функций и выбору мостов во всех трёх средах.

**Нельзя делать иначе.**

- Не заводить локальную таблицу пределов в модуле. Если среде нужны свои значения — это новый профиль в `sandbox-profiles.js`.
- Не выражать запрет нулём. Ноль в `CSF_LIMITS.agent` сохранён только как производное значение для обратной совместимости экспортируемой таблицы; механизм — `forbidden`.
- Не фильтровать способности по профилю перед `selectBridges`. Отказ должен приходить от заглушки моста, которая называет профиль.

**Усложняется.** Появляется косвенность: чтобы понять, почему серверная функция упёрлась в предел, нужно открыть `sandbox-profiles.js`, а не файл исполнителя. Компенсируется тем, что раньше вместо одной косвенности было три расходящихся копии.

**Обратная совместимость.** Существующие автоматизации, воркспейсные тулы и серверные функции работают без правок. Значения профилей `automation` и `workspaceTool` совпадают с прежними; у `serverFunction` изменён только бюджет чтений (10 → 30) — в сторону послабления.

**Одно поведенческое изменение.** Бюджеты `agent` (20) и `teamchat` (50) в профиле автоматизаций теперь действительно действуют. Раньше они были объявлены, но не проверялись, то есть фактически безлимитны. Автоматизация, делавшая больше 20 делегирований или больше 50 сообщений в тимчат за прогон, теперь упрётся в объявленный предел — это восстановление заявленного поведения, а не новое ограничение.

## Что это уже сломало

Три дефекта, найденные при унификации, каждый — прямое следствие дублирования:

1. **Бюджеты `agent` и `teamchat` не действовали в автоматизациях и воркспейсных тулах.** Объект счётчиков в `createBridge` перечислял только `query/mutation/fetch/ai`. `counters.agent++` давал `NaN`, `NaN > 20` — ложь. Делегирование агентам и отправка в тимчат из скрипта были не ограничены ничем.
2. **`moveChildren` не подключался в воркспейсных тулах.** Рукописная карта `BRIDGE_REF_NAMES` в `sandbox.js` его не содержала, хотя `CAPABILITY_MAP.write` его выдавал. Вызов падал с `Cannot read properties of undefined (reading 'apply')`.
3. **Серверные функции не вычищали `__`-глобали.** Воркспейсные тулы удаляют сырые `ivm.Reference` из глобального объекта после бутстрапа; серверные функции — нет, хотя код репозитория наименее доверенный из трёх.
