# ADR-023: Вызов серверной функции codespace как действие автоматизации

**Статус:** accepted

> Номер 023, а не 022: 022 уже занят в ветке `fund-docs-bridge` (ADR-022 «Профили песочниц»), которая на момент написания не влита в master. Разрыв в нумерации на master закроется при её вливании.

## Контекст

Серверные функции codespace — файлы `api/<name>.js` в git-репозитории воркспейса. Они исполняются в изолированной песочнице `codespace/server-fn-executor.js`: отдельный изолят на вызов, 64 МБ, 15 с, способности объявляются комментарием `// capabilities:` в самом файле и открывают только соответствующие мосты.

До этого решения у `executeServerFunction()` был ровно один вызывающий — `POST /:db/portal/api/fn/:repo/:name` в `portal/router.js`. То есть код репозитория можно было запустить только HTTP-запросом из портала, то есть только в ответ на действие живого пользователя. Поставить его на расписание было нечем: у автоматизаций около сорока типов действий, но ни одного, который дотягивается до репозитория. Ближайший, `run_script`, исполняет строку кода, лежащую в конфиге самой автоматизации, — это другой источник кода, без версионирования, ревью и переиспользования.

Практическая нехватка: внешний мониторинг фонда ФСТ написан как серверные функции, а запускать его по расписанию было нечем.

## Решение

Новый тип действия автоматизации `run_server_function`, реализация — `automations/run-server-function.js`, вызов из `automations/execution.js` тонким `case` (тот же приём, что у `update_related_records` → `update-related.js`).

```js
{ type: 'run_server_function', repo: 'monitoring', fn: 'check-sources',
  args: { org: '{{req_501}}' }, resultVar: 'mon',
  idempotencyKey: 'daily-{{today}}', idempotencyMinutes: 1 }
```

`repo`, `fn`, `idempotencyKey` и все строковые значения `args` проходят обычное разрешение шаблонов `{{...}}`, поэтому идентификаторы конкретного воркспейса не попадают в код платформы.

### Песочница не дублируется

Действие не заводит ни своей песочницы, ни своей карты способностей, ни своей таблицы лимитов. Оно вызывает `executeServerFunction()` — тот же вход, что и портал, — и получает те же ограничения. Это сознательно: три среды isolated-vm уже разошлись из-за того, что каждая несла собственную таблицу лимитов, и добавлять четвёртую точку расхождения нельзя. Когда ADR-022 (профили песочниц) будет влит, этому действию менять нечего — оно ограничений не объявляет.

### Идемпотентность

Действие, вызываемое по расписанию и уходящее во внешнюю систему, обязано иметь защиту от повторного срабатывания. Однажды автоматизация без такой защиты создала 452 мусорные отгрузки.

Защита включена по умолчанию и хранится в существующей таблице `_v2_automation_cooldowns` (новая таблица не заводится). Единица идемпотентности — `repo + fn + args + запись`; аргументы хешируются, чтобы большой payload не раздул ключ. `idempotencyKey` позволяет задать единицу вручную.

Заявка берётся одним оператором:

```sql
INSERT INTO ..._v2_automation_cooldowns AS c (automation_id, cooldown_key, last_fired_at)
VALUES (?, ?, NOW())
ON CONFLICT (automation_id, cooldown_key) DO UPDATE SET last_fired_at = NOW()
WHERE c.last_fired_at < NOW() - make_interval(mins => ?::int)
RETURNING c.automation_id
```

Вернулась строка — заявка взята, можно исполнять. Не вернулась — исполняет кто-то другой либо окно ещё не истекло.

### Защита обязана не заклинивать

Это вторая половина требования, и она важнее первой. Разбор охранника отгрузок СДЭК показал состояние, в котором защита глушила всё навсегда: охранник брал сессионный advisory-lock, а каждый его `break` выходил из `switch` мимо строки разблокировки. Соединение возвращалось в пул с удержанным локом, и все последующие попытки получали `false` от `pg_try_advisory_lock` — восемь попыток, ноль отгрузок.

Отсюда два свойства конструкции:

1. **Никакого состояния уровня сессии.** Заявка — строка в таблице с отметкой времени, а не advisory-lock. Упавший между заявкой и завершением процесс не оставляет ничего, что нужно было бы освобождать: заявка истекает вместе с окном.
2. **Провал снимает заявку.** Если функция бросила исключение, заявка удаляется, и следующий запуск повторяет вызов. Иначе одна недоступность внешнего сервиса выключала бы автоматизацию на всё окно.

Проверено на живом PostgreSQL, не только на моках:

| Сценарий | Попыток | Исполнений |
|---|---|---|
| Быстрые повторы, функция успешна | 8 | 1 |
| Функция падает каждый раз | 8 | 8, остаточных заявок 0 |
| Окно истекло между попытками | 2 | 2 |
| Три разные записи | 3 | 3 |
| Одновременные заявки на один ключ | 20 | 1 |

## Последствия

- Код репозитория становится запускаемым по расписанию, ревью и версионирование остаются в git.
- `run_server_function` — значение поля `type` внутри `create_automation` / `update_automation`, а не отдельный инструмент ИИ. Записи в `TOOL_DEFS`, `tool-executor`, `risk-tiers` не требуется; уровень риска наследуется от `create_automation` (TIER_HIGH).
- `idempotencyMinutes` нужно держать меньше интервала расписания. Большее значение молча пропустит часть запусков — это задокументировано во всех трёх точках объявления и в подсказке интерфейса.

## Альтернативы

- **HTTP-вызов через `http_request` на портальный маршрут.** Требует портального JWT, идёт через сеть ради внутрипроцессного вызова и не имеет защиты от повторов.
- **Копировать код функции в `run_script`.** Теряются git, ревью и переиспользование; две копии кода расходятся.
- **Своя песочница внутри модуля автоматизаций.** Четвёртая таблица лимитов — ровно то расхождение, которое ADR-022 устраняет.
