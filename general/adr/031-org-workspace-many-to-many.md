# ADR-031: Организация ↔ область «многие ко многим»

## Статус
Принято (2026-09-15).

## Контекст
`_v2_workspaces.org_id` — скаляр, область состоит максимум в одной организации.
Нужна принадлежность нескольким: холдинг с дочерними юрлицами, общие сервисные
области на несколько команд. FK на колонке нет, attach держит проверку-потом-запись
(TOCTOU), запрос наследования роли скопирован восемь раз (audit §0 плана
2026-09-15-org-workspace-many-to-many.md).

## Решение
1. Связь — таблица `_v2_org_workspaces (org_id, workspace_id)`, UNIQUE-пара,
   FK в обе стороны с ON DELETE CASCADE, индекс по workspace_id.
2. Роль в области = MAX(прямое членство, членство в ЛЮБОЙ организации области);
   владелец области — owner. Единый носитель семантики — role-utils.js.
3. Attach идемпотентен: `INSERT … ON CONFLICT DO NOTHING` (TOCTOU решён UNIQUE);
   409 «already belongs to another organization» исчезает вместе с ограничением.
4. Ответы API несут `orgs: [{id, slug, name}]`; поле `orgId` удаляется в том же
   выпуске (клиенты его не читают — audit §0 С8).
5. Связи не переносятся при копии области: уровень организации, как `_v2_orgs`
   (ADR-026-стиль); в реестр переноса и DDL_EXEMPT junction не вносится.

## Последствия
+ Множественная принадлежность без миграции данных клиентов.
+ Один SQL-фрагмент вместо восьми копий.
− Наследование доступа расширяется с каждой связью: attach требует админа
  области, но членам N организаций роль даёт максимум по всем — аудит доступа
  ведётся по junction, не по колонке.
− Один выпуск несёт заливку из колонки и DROP: откат возможен только до DROP
  (заливка обратима, колонка после DROP — нет).
