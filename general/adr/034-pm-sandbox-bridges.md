# ADR-034: PM-мосты песочниц (pmQuery/pmCreate) под способностью `pm`

**Статус:** accepted

## Контекст

Код песочниц (server functions codespace, скрипты автоматизаций) не видит PM-сателлиты
воркспейса: карта способностей (`utils/sandbox-profiles.js`, ADR-022) не содержит ни
одной способности, дотягивающейся до `pm/service.js`. Практическая нехватка —
«машинка задач фонда» (спека «машинка задач фонда v2», документ #37 fund-demo): её
серверные функции не могут ни ответить справкой об открытых задачах исполнителя, ни
создать задачу для нескольких исполнителей — сегодня это умеет только REST-слой, то
есть живой пользователь.

## Решение

Два тонких моста над `pm/service.js` в новом `automations/sandbox-pm.js`:

- `pmQuery(pool, db, opts)` — чтение: только открытые статусы, задачи любого
  уровня (подзадачи не отсекаются), урезанный ответ (`number`, `title`,
  `status`); фильтры `assigneeId` | `reporterId` | `q` (подстрока по
  заголовку/описанию без регистра), `limit` (умолчание и потолок 10). Без
  единого фильтра — отказ VALIDATION_ERROR: безусловный список всех задач
  песочнице не нужен.
- `pmCreate(pool, db, opts)` — создание: тип всегда `task`, обязательны
  `title`, `assigneeId` и `reporterId`; отсутствие `reporterId` — отказ
  VALIDATION_ERROR. Мост не подставляет владельца области вместо отсутствующего
  автора — задач-сирот из песочницы не бывает; ответ `{ id, number }`.

Способность `pm` (`pmQuery`, `pmCreate`) заводится в `CAPABILITY_BRIDGES`
одним объявлением — `parseCapabilities` серверных функций и `selectBridges`
выводятся из той же карты. Счётчик `pm` — отдельный род в `COUNTER_KINDS`,
`BRIDGE_COUNTER` ведёт оба моста на него; бюджет `pm: 10` объявлен только в
профиле `serverFunction` (ADR-022): в профилях, где счётчик не забюджетирован,
мост отказывает «capability недоступна в профиле» — штатный механизм
`createBridge`, заводить `forbidden` не нужно.

Мосты сами прав не проверяют — как `kag_search` (ADR-023 о повышениях), защита
живёт выше: чтение идёт через `listIssues` без судьи, запись через `createIssue`
с явным `reporterId`, который песочница обязана назвать сама.

## Границы

- Только профиль `serverFunction`; `automation`/`workspaceTool` мост не получают.
- Бюджет `pm: 10` вызовов на исполнение — чтение и запись бьются в один счётчик.
- Только открытые статусы; закрытые (`done`, `canceled` и их синонимы) из
  выдачи `pmQuery` исключены.
- История, чеклисты, комментарии, метки, доски — вне мостов; только чтение
  карточки и её создание.

## Альтернативы

- Делегирование агенту (`delegateToAgent`): непредсказуемо по стоимости и
  времени, отклонено владельцем для этой задачи.
- Прямой SQL из песочницы к PM-таблицам: запрещён — обходит RBAC и схему.
- Разрешить `pmQuery` без фильтров: безусловная выгрузка задач области в
  наименее доверенной из трёх сред; вместо лимита нужен обязательный фильтр.

## Последствия

- «Машинка задач фонда» может отвечать справкой и плодить задачи нескольким
  исполнителям из серверных функций — без единого нового HTTP-входа.
- Открытый статус определяется перечнем имён в мосте, а не `kind` из таблицы
  статусов: запрос `kind` стоит второго похода в базу на вызов. Новый закрытый
  статус, чьё имя не попадёт в перечень, будет сочтён открытым — цена осознанная,
  перечень из четырёх имён покрывает сид и существующие доски.
- Каждая новая песочница, где нужен PM, обязана объявить бюджет `pm` в своём
  профиле явно — молча доступ не расширяется.
