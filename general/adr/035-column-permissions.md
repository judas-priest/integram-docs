# ADR-035: Права на уровне колонки и ячейки (`_v2_column_rules`)

**Статус:** accepted (PM-570)

## Контекст

Права платформы двухуровневые: грант уровня ТИПА (`_v2_grants`, NONE/READ/WRITE/ADMIN) и
правило уровня СТРОКИ (`_v2_row_rules`, ADR в коде `row-permissions.js`: OWNER_ONLY /
ROLE_ONLY / FILTER / DENY_ALL, «only narrows, never expands»). Колонкового и ячейкового
уровня нет: колонку можно защитить только тем, что не отдать роль целиком. Кейс PM-570 —
«колонку «Ставка» видят все, правит один; колонку «Зарплата» в той же таблице читает
только HR».

## Решение

Продолжить ряд «тип → строка → колонка» третьим сателлитом по образцу строковых правил:

```
_v2_column_rules (
  id, type_id, role_id, req_id,
  action CHECK (action IN ('READ','WRITE')),
  created_by
)
```

- **Семантика сужения, как у `_v2_row_rules`:** строка правила = запрет (DENY) действия
  `action` на колонку `req_id` для роли `role_id` (0 = все роли). Нет правила — действует
  грант типа без изменений. Правило никогда не расширяет доступ. Отдельная колонка
  `effect` не нужна: разрешающих правил модель не имеет — разрешает по-прежнему грант.
- **Ячейка = конъюнкция.** Ячейковое право не заводится отдельной сущностью: ячейка
  закрыта, если закрыта её колонка ИЛИ её строка. Обе проверки уже стоят на одних путях
  (грант → строчное правило → колонковое правило), пересечение возникает само.
- **Точки применения (этот этап):** запись — единственная воронка `saveRequisites`
  (REST, инструменты ИИ, финмодель, публичные формы идут через неё) до первой записи
  пакета: `COLUMN_FORBIDDEN` 403 с перечнем номеров колонок; чтение — `getObject`
  (замаскированные колонки вырезаются из `requisites` и перечисляются в
  `restrictedColumns`), метаданные `getType` — флаг `noWrite` на колонке для редакторов.
  Администрирование — REST `schema/column-rules` (admin).
- **Кэша нет** (как у `_v2_row_rules`): правило колонки — редкая запись, проверка —
  один индексный запрос на операцию.

## Осознанные остатки (не в этом этапе, перечень обязателен при продолжении)

Проверка стоит в ядре записи/чтения записи. Следующие пути её ПОКА НЕ проходят и обязаны
быть закрыты до предъявления функции пользователям как «права»:

- отчёты (`reports/service.js`) и sandbox `query` — колонковые DENY в SELECT не
  подставляются; CSV-экспорт и экспорт ИИ;
- `flat-views` (`schema/flat-views.js`) — VIEW над квинтетами мимо всех правил;
- коннекторы — пишут EAV напрямую мимо `saveRequisites` (известная грабля модуля);
- портал (`portal/row-rules.js` — аналог для строк) и публичные формы;
- MCP-паритет (`get_table` не отдаёт `noWrite`), UI администрирования правил.

## Последствия

- Запись чужой колонки из формы агента падает громко (403 с перечнем), а не молча
  выкидывается — различение «нет прав» и «нет колонки» сохранено.
- Чтение с маской меняет форму ответа `getObject` (появляется `restrictedColumns`);
  читатели, складывающие `requisites` в плоскую форму, обязаны переживать отсутствие
  ключа так же, как отсутствие значения.
- Скрытая на чтении колонка не защищена от путей остатка — до их закрытия правило
  читается как «не показывать в карточке», не как «секрет».
