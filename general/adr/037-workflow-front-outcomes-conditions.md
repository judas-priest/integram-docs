# ADR-037: Фронт ожидаемых событий, исходы решений и условия применимости в workflows

Дата: 2026-09-30. Статус: принято. Наследник ADR-036 (модуль process-spec).

## Контекст

ADR-036 задаёт состояние объекта последней строкой журнала: переход судится по
`next_keys` последнего события. Процесс v2 событийной спеки фонда (PR #275,
issue #264) требует шире:

1. Параллельные ветви с AND-join (`chk.dd…chk.gov` → `chk.verdict`): после
   стартового события ожидаются ПЯТЬ событий, и запись второго параллельного
   должна оставаться легальной после записи первого.
2. Решения с исходами (XOR): у решения УТ исход «Отклонить» обязан УБИРАТЬ
   ветку «Одобрить» из ожидаемых, а не оставлять обе.
3. Условные шаги: событие существует только у объектов, для которых условие
   истинно (`ТАРИФ`, `КОНС`, `ОСТ1`…).
4. Сигналы: событие, порождённое таймером, оповещает, но не двигает процесс.

Индустриальные референсы: Workflow Patterns (Parallel Split/Synchronization,
Exclusive Choice), BPMN exclusive gateway + conditional flows, Zeebe
(append-only лог + replay), Temporal (сигнал не меняет состояние, если это
не смоделировано). Все зрелые движки проверяют инварианты в write model;
клиентский показ не может быть судьёй.

## Решение

1. **Фронт.** Состояние объекта = множество ожидаемых ключей: объединение
   переходов всех состоявшихся событий минус состоявшиеся ключи. Переход и
   чтение судят один и тот же вычислитель (`semantics.js`), а не два разных.
2. **Исходы.** Спека решения несёт `outcome_field` (какое поле выбирает
   ветвь) и `out_next` JSONB (исход → csv переходов). Состоявшееся событие
   решения с полем `outcome_field` переводит фронт на выбранную ветку;
   прочие ветки гаснут. Без исхода поле действует как обычный `next_keys`.
   Решение обязано иметь ≥ 2 исхода и пустой `next_keys` (валидатор).
3. **Условия.** Реестр `_v2_workflow_conditions (process, name, set_by)`:
   значение условия пишется setBy-событием журнала полем с именем условия.
   Событие с `when_cond` не ожидается, пока setBy не состоялся; при
   известном ложном значении событие исчезает из доступных, а гейт на него
   считается выполненным (нужен другой вариант выбора). `when_cond` — csv
   имён условий, все обязаны быть в реестре (валидатор).
4. **Сигналы.** `kind='signal'`: пишет только актор «система» (таймеры уже
   пишут от его имени), не имеет `next_keys`, не источник фронта и не
   кандидат; обязан порождаться таймером (валидатор). Журнал сигнала —
   обычная append-only строка.
5. **Обратная совместимость.** Колонки новые, `kind` по умолчанию `step`.
   Для линейных процессов без решений/условий фронт совпадает со старой
   семантикой next(last) — существующие спеки и журналы не мигрируют.

## Последствия

- Гейт (`gate_requires`) сохраняет глобальную семантику «ключ в прошлом
  объекта (любой процесс)» с одним уточнением: ключ условного события с
  известным ложным условием гейт не блокирует.
- Круги (сброс фактов), этапы + 304, кросс-объектные предусловия, группы
  ролей — НЕ входят; их место в следующих ADR/планах.
- Стол fund-demo (`events-desktop.vue`) имеет собственный движок; перевод
  его на API модуля — отдельная работа.
