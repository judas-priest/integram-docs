# 042. Свои поля PM в eav-хранилище — passthrough по алиасам, read-only в PM-интерфейсе

Статус: accepted
Дата: 2026-10-24
Контекст: pm-eav этап 3 (Task 5)

## Проблема

В eav-хранилище PM задачи — записи типа «Задачи» в EAV области, и пользователь
может досыпать типу колонки штатным конструктором схем (`POST /schema/:typeId/columns`).
Служба PM (pm-eav) читает только фиксированный набор реквизитов (номер, статус,
исполнитель, …) — досыпанные колонки в задаче молча невидимы: ни один PM-маршрут,
ни один инструмент их не отдаёт. Пользователь, добавивший колонку, не получает
никакого отклика — отсутствие поля опаснее пустого.

## Решение

- **Чтение — passthrough по алиасам.** Единый сборщик строк задач
  (`pm-eav/issues.js`, `loadIssueRowsByIds` — его реюжат `getIssue` и
  `loadCardByIds`, то есть и карточные списки доски) после фиксированных JOIN-ов
  добирает хвост кастомных колонок ОДНИМ батчем на всю выборку:
  `WHERE up IN (…) AND t IN (…)` — раскладка IN, не `ANY(?)` (execSql
  подставляет параметры скаляром; ANY с массивом падает на живой базе).
  Какие колонки «кастомные», решает сверка с фиксированным набором
  (`FIXED_ISSUE_COLS`): алиасы берутся из `ctx.reqs` через канонический
  парсер платформы `aliasOfColumnDef` — второго классификатора не заводится.
- **DTO аддитивен.** Контракт `IssueDto` passthrough (`contract.js`): кастомные
  колонки кладутся в DTO по своим алиасам верхнего уровня. Ключ появляется
  только при наличии значения — отсутствие не подменяется пустотой.
- **Интерфейс — read-only.** Секция «Свои поля» в `IssueDetail.vue` показывает
  значения без правки. Запись кастомных колонок остаётся за службой объектов
  (`PATCH /objects/...`), а не за PM-маршрутами: у PM нет валидаторов чужих
  колонок, и дублирование слоя записи объектов в PM создало бы второй источник
  истины. Id хранилища фронт берёт из `GET /pm/eav-type` (сами PM-типы скрыты
  из перечня `GET /schema` штампом `module='pm'`), перечень колонок —
  `GET /schema/:typeId`.
- **Правка участниками задачи не охватывается.** Кастомные колонки не входят в
  историю, события `pm.issue.*` и bulk-операции PM — это поток объектов, не поток
  PM.

## Последствия

- Что нельзя делать иначе: не заводить в PM собственную таблицу «кастомных
  полей» и не писать их PM-маршрутами — схема принадлежит конструктору схем;
  PM только читает.
- Что упрощается: колонка, добавленная пользователем, видна в задаче без
  изменений кода PM; новые фиксированные поля добавляются одной строкой в
  `FIXED_ISSUE_COLS`.
- Что усложняется: список `listIssues` (таблица) хвост не добирает — свои поля
  видны в карточке задачи и на карточках доски (`loadCardByIds`), в табличном
  списке их нет до отдельного решения (ещё один JOIN-пакет на страницу списка).
- `ensureParticipantsCol` (этап 3 Task 3) следует той же модели: ленивая
  колонка со штампом `:ALIAS=`, скрытая от «кастомности» включением в
  фиксированный набор.
